# #86 Input is level-sampled across a catch-up batch, so taps vanish and holds multiply

## What to build

Input is read once per simulation tick, straight off the live pressed-keys map, with no edge latch and no per-tick queue. One synchronous catch-up batch therefore samples **the same keyboard snapshot N times**: a key held at wakeup is delivered as N ticks of holding, and a keydown plus keyup that both land between two batches is never sampled at all.

What a player sees: after any stutter the bunny lurches in the direction they were last holding, and a quick jump tap during that stutter does nothing at all.

This is a **fairness** bug, not a desync — the frame is stamped, so the whole room agrees on the wrong input. Confirmed by reading; not measured.

## Acceptance criteria

- [ ] A key pressed and released entirely between two loop wakeups is delivered to exactly one tick rather than dropped
- [ ] A key held across a catch-up batch is not multiplied into more held ticks than wall clock elapsed
- [ ] The simulation stays deterministic from a seed — `test/replay.test.mjs` still passes, and nothing in the simulation layer reads a clock or the DOM
- [ ] A headless test drives a catch-up batch with a tap and a hold and asserts the delivered per-tick inputs
- [ ] Local (couch) and networked play deliver the same per-tick input for the same key timeline
