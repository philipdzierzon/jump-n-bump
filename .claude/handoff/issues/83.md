# #83 pump() cannot yield when one tick overruns the frame budget

**state:** open  **labels:** bug, ready-for-agent

> *This was generated by AI during triage.*

## Parent

#81 §1 and §10 — cut out of the loop/relay/flow audit.

## What to build

The game loop advances its frame budget by exactly one 60 Hz frame per iteration and only breaks out of the catch-up `while` when it finds itself ahead of that budget. If one simulation tick costs more wall clock than one frame, the remaining budget is monotonically decreasing and **the break is never reached**. The loop is then a synchronous infinite loop: no draw, no keyboard, no socket read, no timer yield. The only exit is the pause taken when a match limit is reached — which, in an endless match (the default), never comes.

Two live entrances, neither exotic:

- **A device that cannot sustain 60 Hz.** #51 measured simulation p95 at 4–7 ms on an iPhone against a 16.67 ms budget. That is the whole margin: a slightly slower device, or one bad GC inside a tick, starts the compound and never recovers.
- **A peer stamping far ahead.** When the room reports a positive gap the loop takes a `continue` that skips both the draw and the yield, and the gap is driven by a value any peer can raise by up to the catch-up ceiling. One peer stamping ahead every tick pins every other client in that branch: one drawn frame per several thousand simulated ticks.

The comment in the loop asserts the opposite — "a slow client loses frames, never simulation state". That holds up to a debt the loop can pay off inside one wakeup, and not past it. Past it the client loses the tab.

**This is also the measured root of the desync mode.** `docs/research/desync-under-load.md` §1 and §7: a 6×-throttled client sent 936 of 955 frames late — 98% of the stream — against an in-process relay, and §7 names the cause exactly: the loop steps its whole tick backlog synchronously before the event loop delivers the incoming input messages. #71 was specified, built and measured against that and bought nothing, because a client cannot compute a deadline from data it has not read yet.

**Bound the batch, yield, do not skip.** A skipped tick is a divergence, so skipping is wrong. Yielding is not: the ticks still run, spread across wakeups, and the client is simply behind — which the relay already handles with substitution, AI takeover and resync (#40, #42). This is also the only change that makes a struggling client's frames reach the socket *during* the backlog rather than after it, which is the thing #70 measured and #71 could not reach from the stamp side.

## Acceptance criteria

- [ ] The loop always yields to the event loop within a bounded number of simulation ticks, however long an individual tick takes
- [ ] No tick is ever skipped — a client that falls behind runs every tick, spread across wakeups, and is simply behind
- [ ] The positive-gap sprint path is subject to the same bound as the ordinary path
- [ ] A headless test makes one simulation tick cost more than a frame budget and asserts the loop yields rather than spinning; it uses a fake clock and does not need a browser
- [ ] The comment claiming a slow client "loses frames, never simulation state" is corrected to state the bound that now makes it true
- [ ] `test/replay.test.mjs` is unaffected — it steps the simulation by hand and never enters the loop
