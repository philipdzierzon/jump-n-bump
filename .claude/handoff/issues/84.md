# #84 Room state does not survive a match boundary

**state:** open  **labels:** bug, ready-for-agent

> *This was generated by AI during triage.*

## Parent

#81 §3 and §7 — cut out of the loop/relay/flow audit.

## What to build

Three bugs in `Room`'s per-match state, all in one file, all small.

**A — the high-water stamp is never reset, so a second match on one `Room` starts already finished.** The room tracks the newest tick any peer has stamped; the `start` handler resets the tick, the input map and the driver map, and leaves the high-water mark alone. The normal flow hides this, because a match end routes to the lobby, which tears down the session and builds a fresh `Room`. Two paths keep the `Room` alive across a `start`: a client still on the match screen inside the two-second end-of-match freeze when the host starts the next one (the session builder's own comment says this happens), and a client that reconnects into the room as the next match begins. Either way match 2 opens at tick 0 with a high-water mark from match 1, so the reported gap is a few thousand ticks, the loop takes its sprint branch, and the client steps thousands of ticks synchronously with no draw. Its frames then flood out stamped 2…2700, which raises the relay's tick and drags every other client's high-water mark with it.

**B — catch-up ignores whether the match is still playing and steps past the end.** The end-of-match flag then latches and the start call no-ops forever. A client that joins a match in its final second lands in a permanently frozen session.

**C — driver changes stamped for a tick already stepped are never applied and never collected.** Entries go into the driver map keyed by tick and are deleted only for the tick currently being stepped, so an entry for a passed tick leaks and its change is lost: the client keeps driving a seat the room has already given to the AI.

## Acceptance criteria

- [ ] Starting a second match on a live `Room` opens with a gap of zero, and the loop does not take its catch-up path on the first tick of that match
- [ ] A client held in the end-of-match freeze when the host starts the next match joins that match at its real tick
- [ ] Catch-up stops at the end of the match rather than stepping past it; a client that joins in a match's final second reaches the board and can play the next match
- [ ] A driver change stamped for a tick that has already been stepped is either applied or discarded explicitly, and does not accumulate in the driver map
- [ ] The driver map does not grow without bound over a long match
